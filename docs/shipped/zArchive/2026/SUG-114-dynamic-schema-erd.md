# SUG-114 — Dynamic schema ERD

Replace the static, hand-maintained `schemaManifest.js` with an auto-generated artefact produced at build time from the actual Sanity schema source, so the content model diagram at `/platform/cms` stays accurate without manual intervention.

## Background

`apps/web/src/data/schemaManifest.js` is an 810-line file generated by `scripts/generate-schema-manifest.mjs`, which walks `apps/studio/schemas/documents/` and `apps/studio/schemas/objects/`, parses TypeScript source via regex, and emits the `entities[]` and `relationships[]` arrays consumed by `SchemaERD.jsx`.

The generator already exists and works. The problem is that it is a manual step — `pnpm generate:schema-manifest` — not wired into the build or CI pipeline. Every schema change (new type, renamed field, new reference) silently drifts from what the ERD shows until someone remembers to regenerate. The file has a `// Last generated: YYYY-MM-DD` header that currently reads 2026-05-13 and will age.

The fix is to run the generator automatically so `schemaManifest.js` is always current.

## Objective

After this epic, the content model diagram reflects the actual deployed schema with no manual step. The `schemaManifest.js` file is regenerated automatically on every build (or on every schema-touching commit). The `// Last generated:` date in the file header is always today's date, not a historical one.

## Scope

**Phase 1 — Wire generator into the build pipeline**

- [ ] Add `generate:schema-manifest` as a `prebuild` or Turbo pipeline step in `apps/web/package.json` (or root `turbo.json`) so it runs before Vite bundles the app — layer: tooling
- [ ] Confirm `schemaManifest.js` is in `.gitignore` (or add it) so the generated file is not committed — the source of truth is the schema TypeScript, not the artefact — layer: tooling
- [ ] Update the `// DO NOT EDIT` header comment to clarify it is generated at build time, not on demand — layer: docs
- [ ] Verify the Netlify build produces a fresh manifest (confirm `pnpm build` triggers the generator in CI) — layer: infra
- [ ] Update `docs/conventions/schema-conventions.md` to document the pipeline: "schema changes are reflected in the ERD automatically on next build; no manual regeneration needed" — layer: docs

**Phase 2 — Generator accuracy pass**

The current regex parser has known gaps: it misses fields defined via spread patterns, inlined `defineArrayMember` chains, and schema types that import shared field definitions from `schemas/fragments/`. An accuracy pass before SUG-20 ships ensures the diagram is trustworthy when it goes live at `/platform/cms`.

- [ ] Audit `schemaManifest.js` output against actual Studio schema for 3 representative types (one content doc, one taxonomy, one complex object like `ctaButton` or `richImage`) — identify any fields missing from the manifest — layer: tooling
- [ ] Fix any regex gaps found in the audit — layer: tooling
- [ ] Add a count assertion at the end of the generator: if `entities.length < N` (current baseline: ~29 types), fail with a clear error message so silent regressions are caught — layer: tooling

## Technical notes

- **Current pipeline entry point:** `scripts/generate-schema-manifest.mjs` — invoked via `pnpm generate:schema-manifest` in root `package.json`. The simplest wiring is a `prebuild` script in `apps/web/package.json`: `"prebuild": "node ../../scripts/generate-schema-manifest.mjs"`. Turbo's `pipeline.build.dependsOn` can also be used if a separate Turbo task is preferred.
- **Gitignore:** `schemaManifest.js` should be treated like `stats.json` — generated at build time, not committed. Check whether any CI step depends on it being present in the repo before removing it.
- **Vite dev server:** in development, the manifest is generated once on server start (via `prebuild` or a separate `predev` script). If the schema changes mid-session, the developer runs `pnpm generate:schema-manifest` manually — acceptable for dev; CI handles production.
- **Relationship to SUG-20:** SUG-20 is a component/CSS refactor of `SchemaERD.jsx`. This epic is a data pipeline change. They are independent and can run in parallel, but SUG-114 Phase 2 (accuracy pass) should complete before SUG-20 ships so the live diagram is correct.
- **Model recommendation:** `haiku` (pure tooling/config work).

## Non-Goals

- No changes to `SchemaERD.jsx`, its props API, or its visual rendering — that is SUG-20's scope.
- No runtime GROQ fetch of the deployed Sanity schema. The generator reads TypeScript source; it does not call the Sanity API. Runtime introspection would require a build-time API call with credentials and adds CI complexity for no UX benefit (the schema only changes when a developer commits to the repo).
- No new schema types or Studio changes.
