# Alignment Audit — Sugartown Token Pipeline vs. "What Are Hypertokens?" (UX Collective)

**Date:** 2026-07-02
**Standard source:** https://uxdesign.cc/what-are-hypertokens-the-layer-between-tokens-and-components-rebuilt-for-agents-962dbe93e0c4
**Scope of ecosystem reviewed:** `tokens/source/tokens.json`, `sd.config.mjs`, generated `tokens.css` (both copies), `docs/conventions/token-naming.md`, `apps/web/scripts/validate-tokens.js`, DS component directories (`apps/web/src/design-system/components/`, `packages/design-system/src/components/`), and component CSS consuming heading tokens (`ContentBlock.module.css`, `PageSections.module.css`, `Hero.module.css`, `RichText.module.css`, `TrustReportSection.module.css`)

## Summary

The article's core claim is that plain design tokens fail when a decision spans multiple CSS properties at once (e.g. a heading = font-family + size + weight + line-height + letter-spacing), and proposes a "hypertoken" layer — a named, compiled bundle that every consumer (CSS, Figma, native, agents) reads from a single source, instead of hand-copying the cluster everywhere it's needed. Sugartown's token pipeline is **exclusively single-property** (656 tokens, all `$type: color` or `$type: other`, one flat `$value` each) — there is no composite/bundle token type anywhere in `tokens.json`, and no component in either DS layer represents a reusable typography/surface bundle. Direct evidence of the exact failure mode the article describes was found live in the codebase: the `heading-2` style (font-size + font-weight + color) is hand-re-declared identically across at least 6 separate CSS files, with line-height inconsistently included, omitted, or hardcoded (`line-height: 1.3`) rather than token-referenced. Of 6 dimensions extracted from the article, this ecosystem scores 1 Match, 3 Drift, 1 Gap, 1 N/A.

## Recommendations

- **Introduce a typography-bundle layer before touching component CSS.** The heading drift (Drift, row 2) is the cheapest, highest-signal fix: define `--st-heading-{1..4}` (or a `Heading`/`Text` DS component) that resolves font-family + size + weight + line-height + letter-spacing as one unit, then migrate the ~9 known call sites off hand-assembled combos. This directly closes rows 1–3.
- **Extend `validate:tokens` (or a new script) to catch property-cluster drift**, not just unresolved `var()` refs — e.g. flag any selector that sets `font-size: var(--st-font-heading-*)` without an accompanying `line-height` token reference. Cheap to add given the validator already parses component CSS.
- **If AI-agent-assisted styling work is a goal** (this session, Claude Code sessions generally), consider a machine-readable style manifest (JSON: concept name → resolved token set) generated in the same `tokens:build` step, even if it isn't consumed by CSS at all — this closes the "agents read a list, not a decision" gap named in row 5 without requiring a new authoring format.
- **Figma bidirectional sync** — no action recommended; the premise doesn't match Sugartown's HTML-mock-based design workflow. Revisit only if the design source of truth changes.

## Framing caveats

- The article's cross-*platform* framing (CSS/Figma/iOS/Android all drifting from one design decision) only partially maps to Sugartown, which is a single web codebase with no native or Figma-synced output. The audit reframed the same underlying problem as cross-*file* drift within CSS, which is where the evidence actually showed up — this is a legitimate translation of the standard's intent, not a dodge, but it means a literal "Match" was never possible on that framing even before finding the drift.
- The article is a single practitioner's argued position (referencing Jake Albaugh's pipeline and a Figma-reported case study), not a ratified spec — the W3C composite-token draft it builds on is the only part with any standards backing. Findings here should be read as "does Sugartown solve the problem this article names," not "is Sugartown non-compliant with an industry standard."
