What it is

PageHeader is the identity band component at the top of every content page — the single source of truth for a page's heading, breadcrumb navigation, and contextual metadata.

What it does

  • Renders the page <h1> — owns the heading landmark for the entire page
  • Provides a breadcrumb slot for back-navigation with consistent placement and styling
  • Accepts a media slot (Avatar or Media) for entity and person folio pages
  • Applies a background tint via color-mix at 10% opacity to signal content type
  • Accepts the MetadataCard pattern as a full-width slot below the identity block

What it is not

  • Not a page layout component — it does not set page width, gutter, or scroll behaviour
  • Not a section heading — use SectionLabel for headings within a page's content
  • Not a card header — it spans full viewport width and is not composable inside containers

06Usage Guidelines Must HavePM: buildSB: manual
RULES — Do/Don't grid: maximum 5 per column, one sentence each. Do not repeat Props or Composition content. Focus on boundary conditions, common misuse, and composability pitfalls. No code examples here — that belongs in section 03. Below the grid, add one callout for the most critical non-obvious rule.
Do
  • Use DS colour tokens for the tint prop — never freeform hex values.
  • Pass only the props relevant to your page type — omit slots that don't apply.
  • Build MetadataCard in the app layer from CMS data, then pass as a slot.
  • Place FilterBar below PageHeader in the page layout, not inside it.
  • Use the actions slot for admin/edit controls — keep them to one element.
Don't
  • Don't use eyebrow as a subtitle — it's a type qualifier, not a clarifying sentence.
  • Don't pass count on entity pages — an item count is meaningless for a person or tool.
  • Don't add a second <h1> below the header — this component owns the page's heading landmark.
  • Don't add sticky behaviour inside this component — handle it at the page layout level.
  • Don't nest PageHeader inside a container — it must span the full viewport width.
07Accessibility Must HavePM: buildSB: manual
RULES — Required: semantic structure, landmark roles, ARIA attributes, focus behaviour, and motion. Keyboard interaction table is required only for interactive components — omit if the component has no keyboard interactions. Screen reader notes required when announced output is non-obvious (e.g. count badge, eyebrow casing).
  • ✓
    Heading landmarkThe title prop renders as <h1>. There must be exactly one <h1> per page — do not add a second heading below the component.
  • ✓
    Eyebrow screen reader labelThe eyebrow element carries aria-label matching its text content, so screen readers announce the qualifier without CSS text-transform: uppercase affecting pronunciation.
  • ✓
    Count badgeThe count badge carries aria-label="{count} items" — screen readers read "24 items" rather than the bare number in context.
  • ✓
    Breadcrumb navigationThe breadcrumb slot must receive a <nav aria-label="Breadcrumb">. The DS Breadcrumb component handles this automatically — do not implement a custom breadcrumb.
  • ✓
    Tint contrastTint is applied at 10% via color-mix and does not affect text contrast. All text tokens independently guarantee WCAG AA (4.5:1) on the surface background in both light and dark modes.
  • ✓
    No keyboard interactionPageHeader has no interactive elements of its own. Keyboard behaviour is delegated to slot components (Breadcrumb, actions) — see those components' own docs for keyboard interaction tables.

The within-page heading alternative — use when you need a labelled section heading below the PageHeader, not another page title.
